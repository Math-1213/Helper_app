## Protocolo de Comunicação e Uso das Bridges

O barramento de comunicação entre a **WebView (micro-app)** e o **Core Nativo do Helper** é o coração da plataforma. Embora a troca de dados ocorra de forma assíncrona por meio de eventos nativos (`postMessage`), a arquitetura foi desenhada seguindo os princípios de requisição e resposta do protocolo **HTTP/REST**.

---

### Visão Geral da Arquitetura do Protocolo

1. **WebView (Cliente):** O código JavaScript do micro-app serializa um objeto JSON contendo o módulo desejado, a ação e os parâmetros, enviando-o via `window.ReactNativeWebView.postMessage()`.
2. **Helper Core (Servidor/Roteador):** O método nativo `handleBridgeMessage` atua como um controller central. Ele intercepta a mensagem, faz o _parse_ do JSON, valida as permissões do aplicativo (`PermissionService`) e roteia a requisição para o manipulador específico (`refs[module]`).
3. **Event Listener (Resposta):** O resultado da operação é retornado da camada nativa para a WebView enviando uma string JSON, que é capturada pelo micro-app escutando os eventos `message` e `document.message`.

```
┌───────────────────────────┐                     ┌───────────────────────────┐
│     WebView (Client)      │                     │     Helper Core (App)     │
└─────────────┬─────────────┘                     └─────────────┬─────────────┘
              │                                                 │
              │  1. postMessage(JSON.stringify(payload))        │
              │────────────────────────────────────────────────>│
              │                                                 │──┐ 2. Parse &
              │                                                 │  │    Validação de
              │                                                 │  │    Permissão
              │                                                 │<─┘
              │                                                 │──┐ 3. Execução no
              │                                                 │  │    Módulo Nativo
              │                                                 │<─┘
              │  4. sendToWebView(JSON.stringify(response))     │
              │<────────────────────────────────────────────────│
              │                                                 │
┌─────────────┴─────────────┐                     ┌─────────────┴─────────────┐
│  window.addEventListener  │                     │    handleBridgeMessage    │
└───────────────────────────┘                     └───────────────────────────┘

```

### Estrutura do Payload (Contrato de Mensagem)

#### 1. Envio do Micro-App para o Nativo (Requisição)

O objeto enviado do micro-app para o Helper aceita variações para manter a retrocompatibilidade de nomenclatura (`module`/`bridge` e `params`/`data`):

```json
{
  "module": "location", // Nome da bridge de destino ("module" ou "bridge")
  "action": "GET_CURRENT_LOCATION", // Operação a ser executada
  "params": {}, // Dados de entrada ("params" ou "data")
  "callbackId": "req_171000" // (Opcional) Identificador único para pareamento de resposta
}
```

#### 2. Resposta do Nativo para o Micro-App (Sucesso)

```json
{
  "module": "location",
  "type": "LOCATION_DATA",
  "success": true,
  "data": {
    "latitude": -22.725,
    "longitude": -47.648
  },
  "callbackId": "req_171000"
}
```

#### 3. Resposta de Erro/Bloqueio por Permissão

```json
{
  "callbackId": "req_171000",
  "success": false,
  "error": "Permissão negada para o módulo 'location'.",
  "code": "PERMISSION_DENIED"
}
```

---

### Ciclo de Validação e Segurança Interna (`handleBridgeMessage`)

Sempre que uma mensagem chega ao Core do Helper, o `handleBridgeMessage` executa um fluxo estrito de quatro etapas:

1. **Normalização e Parse:** Converte a string em objeto e extrai as chaves de módulo, ação e parâmetros.
2. **Checagem de Permissões:**

- O sistema consulta o mapa interno (`MODULE_TO_PERMISSION_KEY`). Se o módulo exigir autorização prévia (ex: `camera`, `sensors`, `location`, `file`, `mic`, `storage`), o Helper recupera as permissões atribuídas pelo usuário ao `appId`.
- Se a permissão estiver **desativada**, o Helper exibe um aviso visual nativo ao usuário (`ToastAndroid.show`), cancela a chamada e devolve um payload com o código `PERMISSION_DENIED`.

3. **Resolução de Referência Nativa:** Verifica se o módulo solicitado está registrado no dicionário de referências (`refs`).
4. **Execução:**

- Se o módulo possuir o método unificado `handleAction`, ele é invocado repassando a ação e o contexto do aplicativo.
- Se o módulo expor a ação como um método direto (ex: `targetModule[actionName]()`), ele é chamado passando os parâmetros e o `callbackId`.

### Guia Prático de Implementação no Micro-App

Abaixo estão os padrões em JavaScript para enviar requisições e processar respostas dentro de qualquer aplicação web adaptada para o Helper.

#### 1. Função Utilitária para Envio de Dados

```javascript
// Envia payloads serializados para o contêiner nativo
function sendToApp(data) {
  const payload = JSON.stringify(data);

  if (window.ReactNativeWebView) {
    window.ReactNativeWebView.postMessage(payload);
  } else {
    console.warn(
      "Ambiente fora da WebView do Helper. Payload não enviado:",
      payload,
    );
  }
}
```

#### 2. Registrando o Escutador de Respostas (Listener)

Para capturar o retorno assíncrono e eventos em tempo real (como _streaming_ de câmera ou telemetria de sensores), cadastre ouvintes para os eventos de mensagem da janela:

```javascript
// Garante compatibilidade entre diferentes versões do Android WebView
window.addEventListener("message", receiveMessage);
document.addEventListener("message", receiveMessage);

function receiveMessage(event) {
  let msg;
  try {
    msg = typeof event.data === "string" ? JSON.parse(event.data) : event.data;
  } catch (err) {
    console.error("Erro ao realizar o parse da mensagem da Bridge:", err);
    return;
  }

  // Tratamento dos retornos por módulo
  switch (msg.module) {
    case "location":
      if (msg.type === "LOCATION_DATA") {
        console.log(
          "Coordenadas recebidas:",
          msg.data.latitude,
          msg.data.longitude,
        );
      } else if (msg.code === "PERMISSION_DENIED") {
        alert("Acesso à localização negado nas configurações do módulo.");
      }
      break;

    case "camera":
      if (msg.type === "FRAME") {
        // Atualização de quadro contínuo (Streaming)
        updateCameraCanvas(msg.data);
      } else if (msg.type === "PHOTO_RESULT") {
        console.log("Foto capturada com sucesso!");
      }
      break;

    case "file":
      if (msg.success) {
        console.log("Arquivo selecionado:", msg.uri);
      }
      break;

    default:
      console.log("Mensagem genérica recebida da Bridge:", msg);
  }
}
```

#### 3. Exemplos de Chamadas de Ação

##### Solicitando Geolocalização

```javascript
function usarLocalizacao() {
  sendToApp({
    module: "location",
    action: "GET_CURRENT_LOCATION",
    params: {},
  });
}
```

##### Capturando uma Foto

```javascript
function tirarFoto() {
  sendToApp({
    module: "camera",
    action: "TAKE_PHOTO",
    params: {
      saveToGallery: true,
    },
  });
}
```

##### Iniciando Transmissão Contínua de Câmera (Stream)

```javascript
function iniciarCameraStream() {
  sendToApp({
    module: "camera",
    action: "START_STREAM",
    params: {},
  });
}
```

##### Selecionando Arquivos do Dispositivo

```javascript
function selecionarArquivo() {
  sendToApp({
    module: "file",
    action: "PICK_FILE",
    params: {},
  });
}
```

### Referência das Bridges Disponíveis

Cada módulo de ponte nativa possui métodos, ações e formatos de resposta específicos. O detalhamento completo de cada contrato de mensagem, parâmetros aceitos, tipos de retorno e exemplos de código podem ser encontrados em seus respectivos subtópicos de documentação:

- **2.1 `StorageBridge**` (`storage`) — Persistência local chave-valor isolada por sandbox (`appId`).
- **2.2 `CameraBridge**` (`camera`) — Captura pontual de fotos e streaming de quadros em tempo real.
- **2.3 `LocationBridge**` (`location`) — Obtenção de coordenadas geográficas via GPS nativo.
- **2.4 `SensorBridge**` (`sensors`) — Telemetria inercial e leitura contínua de acelerômetro e giroscópio.
- **2.5 `FileBridge**` (`file`) — Seleção, conversão e manipulação de arquivos locais em Base64.
- **2.6 `MicrophoneBridge**` (`mic`) — Captura e conversão de áudio offline.
- **2.7 `ConsoleBridge**` (`console`) — Redirecionamento de logs da WebView para o terminal nativo para depuração.
